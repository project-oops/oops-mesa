# D003 - Mesa's AMD driver first, a driver of our own second, gated by one measurement


**decided** · 2026-09-14 (assumed at 12:50, the owner said yes at 13:10 the same day)

Made without the owner's word on which route; both were laid out to them the same day and the
first is the one that fits D001. The measurement that decides it costs one run on the
instrument that already exists.

## The choice

The first route tried is **Mesa's existing AMD gallium driver, radeonsi, on a winsys of ours.**
The driver believes it sits on a Linux kernel: it asks a device-information interface for the
chip, the firmware features and the memory limits, and it submits through a kernel command
interface. Those become the winsys and a small patch of constants, which is what this
repository is for. The shader backend is ACO, so no LLVM is built or linked.

The route is gated by one measurement before any winsys code is written: **does the hardware's
driver and its compositor tolerate a client that writes the full graphics state itself on our
queue?** radeonsi owns every register it touches; this week's instrument showed that one wrong
register (a point-list primitive type) starved the system compositor until the system killed
its shell (orbistoun#535). The experiment emits radeonsi's initial-state register set through
oops-gl's existing submission path, with the fence, GPU clock and pixel hash it already records,
and watches the compositor. Pass means the route is open. Fail means the fallback.

The fallback is **a gallium driver of our own** that leans on the vendor graphics library for
state (its exported register defaults, shader linking and command builders), as the closest
prior art does. It is roughly twice the shim, it keeps Mesa's GL, GLSL, address library and
ACO, and it is still a great deal less than the prior art wrote.

## Why

- **The winsys is needed by both routes**, so the experiment costs nothing that is thrown away
  if it fails; only the driver choice waits on it.
- **radeonsi is maintained upstream for this GPU generation.** Every register it programs for
  GFX10.1 is somebody else's problem to keep correct across Mesa releases; our own driver would
  make it ours.
- **The risk is real and specific.** The compositor shares the GPU, and the vendor driver
  expects certain state to be set through its own builders. Nobody has tried a full-state
  client on this firmware; the prior art all went through the library. That is exactly why it
  is a measurement and not an argument.
- **The fallback is proven.** Two public projects render through the library route on
  firmware 12.02 and one on 6.02. If the measurement says no, the shape of the answer is known.

## What the measurement records

The pass condition is stated before the run: the compositor's own frames keep arriving
(no `HP3D` timeout in the system log, no shell restart), our fence and clock retire on every
frame, and the pixel hash of a known frame is unchanged from the oracle record. Anything else
is a fail, recorded with the system-log lines that say why.

## Result

**Pass, 2026-09-14, firmware 12.40** (worklog 002). radeonsi's preamble for this hardware,
generated by the pinned Mesa's own code (`tools/preamble-dump`), ran in front of every frame
of the paused cube for 45 seconds in each of two variants: with `CONTEXT_CONTROL` and
`CLEAR_STATE`, and without `CLEAR_STATE`. The fence and the GPU clock retired on every frame,
the frame hash stayed at the oracle record's `0x9dbfe189` throughout, and the system log
carried no timeout, fault or restart; the shell drew its home screen after each exit. The
platform serves `CLEAR_STATE` on our queue. The first route is taken; the fallback stays
written down in case a later unit finds what this one could not: radeonsi's per-draw state,
shaders and descriptors are unit 6's measurements.
