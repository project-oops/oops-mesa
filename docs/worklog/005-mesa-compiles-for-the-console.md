# 005. Mesa compiles for the console, and the build answers its own questions from measurements

**2026-09-14** - roadmap unit 3 finished properly, and most of what unit 5 needs is now built

## What changed

`./bin/oops-mesa build` exits 0 and produces **48 static archives for `x86_64-unknown-freebsd`**,
including radeonsi for every GFX generation, ACO, NIR, GLSL, Mesa's utility layer, AddressLib and
libdrm's own `libdrm_amdgpu.a`. Upstream Mesa 26.2.2 compiles for this console.

Four things had to exist for that, each of which is now a named piece:

- **D005**, the architecture: libdrm is carried, not replaced. The shim sits under it and answers
  its ioctls. That is a quarter the surface of implementing libdrm's API, and it is what D001
  already committed to.
- **libelf, built for the target** from `contrib/elftoolchain` in the checkout D004 pins, with
  its three m4-generated sources produced exactly as FreeBSD's own makefile produces them.
  radeonsi will not configure without it.
- **The C++ standard library**, staged from the same tree, with FreeBSD's own generated
  `__config_site` and `__assertion_handler`. Mesa is not a C project: ACO is C++, and a C-only
  sysroot stops the build two hundred objects in.
- **A probe archive built from obSCEne's import census**, which is the interesting one.

## The build answers "does this function exist" from evidence

meson decides what Mesa may use by linking small programs, so the answer depends entirely on
what the linker is handed. This went wrong twice before it went right, and both failures are
worth keeping:

| what the linker was given | what every probe said | what it cost |
|---|---|---|
| nothing, undefined symbols allowed | yes | Mesa emitted GCC's `__builtin_add_overflow_p` and ARM FPSCR builtins on an x86-64 target; it surfaced a thousand objects later |
| nothing, undefined symbols refused | no | configure stopped at the first library it thought was missing |
| one empty definition per symbol obSCEne measured `present` | what a sweep found | correct |

So a link probe in this build now answers a real question: **did a measurement on this console
find this symbol?** 10,247 names, from `data/hardware/ps5-imports.txt`. `dlopen` reports present
because a sweep found it. Anything nobody measured reports absent, and Mesa takes its own
portable path, which is the safe direction.

That makes the census a load-bearing input, and it immediately found a hole in it:
**`clock_gettime` is not in the census while `clock_settime` and `sceKernelClockGettime` are.**
A clock with a setter and no getter is a gap in the mine, not a property of the platform. It is
carried in a supplement list with that reasoning written beside it, and
`REQ-20260914T1636Z-4c92` asks obSCEne to replace the argument with a measurement, along with the
twenty-one other names a port of this kind probes for.

## Surprises

- **The evidence base became part of the toolchain.** Nothing planned this. It followed from
  refusing both dishonest answers, and the result is that a gap in obSCEne's census now shows up
  as a Mesa build failure with a name attached. That is a better feedback loop than either
  project had separately.
- **Two headers in this sysroot do not exist in FreeBSD's source.** `osreldate.h` is generated
  from one number in `sys/param.h`, and libc++'s `__config_site` is generated by its build -
  except FreeBSD ships its own copy at `lib/libc++`, which is the authoritative configuration
  rather than a plausible one. Both are now staged the way FreeBSD makes them.
- **Mesa and libdrm both define `handle_table_remove`.** It only shows up in a static
  whole-archive link, which is exactly what a title will do. The build does not hide it: the
  shared-object target that hit it is not one we consume, and the collision is written into
  `build-mesa.sh` as something unit 7 must settle before it packages an SDK.
- **Debian's meson is older than Mesa requires**, and libdrm's test programs try to link
  executables against a libc that is not there. Both are one line each, and both would have been
  invisible without actually running the build.

## A postscript, the same day

`src/winsys/` now exists: the device open, close and ioctl dispatch, with all 22 commands
present and every unimplemented one returning `-ENOSYS` under its own name. It compiles against
Mesa's own kernel interface headers, the staged sysroot and oops-sdk's bindings, which is the
first check that D005's command list is the real one rather than a reading of call sites. Six of
the 22 are marked as the path to a first frame. `AMDGPU_INFO` refuses every query rather than
answering from a PC part, and names the request that would settle it.

## The device description, and the three tiers it is written in

`src/winsys/device_info.c` answers `AMDGPU_INFO_DEV_INFO`, which is where radeonsi asks what the
GPU is and refuses to start without an answer. It would have been easy to fill it from a PC part
of the same family and never say so. Instead each field sits in one of three tiers:

- **measured**, two of them. The GPU clock at 100 MHz, from the end-of-pipe counter oops-gl reads
  every frame; and the 16 KiB page size obSCEne read from `hw.pagesize` on firmware 12.40.
- **classifier**, two of them. The family and revision are not properties of this hardware at
  all: they are the values that make Mesa's own `identify_chip` walk arrive at GFX1013, which is
  the part D003's measurement established this is. Mesa's constants, quoted back to it.
- **assumed**, six groups. Shader-engine and compute-unit counts, render backends, the address
  range, memory type and width, context count, fragment size. Each says why it is plausible.

The function returns how many groups are assumed and logs it, so a frame rendered on this
description can never be mistaken for a frame rendered on measurements. The host suite asserts
that the number is greater than zero, which will start failing usefully once
`REQ-20260914T1558Z-7d41` comes back and the tiers move.

`./bin/oops-mesa test` is real as of this entry: eight checks, covering the classifier values, the
two measured numbers against their records, and that every unimplemented command returns `-ENOSYS`
rather than success.
